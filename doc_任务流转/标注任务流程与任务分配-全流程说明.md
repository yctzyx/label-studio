# Label Studio 二开：标注任务流程与任务分配 — 全流程说明

本文档基于当前仓库代码（`label_studio/`）整理，区分 **Label Studio 原生任务完成语义** 与本 fork **任务工作流（annotate → review → accept → done）**、**团队分配**、**FSM 状态轨迹** 之间的关系，便于联调、排障与扩展。

---

## 1. 两套并行机制（必须先分清）

| 维度 | 原生 LS 机制 | 本仓库二开「任务工作流」 |
|------|----------------|---------------------------|
| **「任务是否算做完」** | `Task.is_labeled`：有效标注数（排除 skip 策略下的 cancelled 等）相对 `Project.maximum_annotations`（及 overlap / skip_queue 等）计算 | **不替代** `is_labeled`；工作流 `done` 时会 **若仍未标记完成则强制 `is_labeled=True`**（见 `workflow_services._mark_task_done`） |
| **谁在干活** | Label Stream：`TaskLock` + overlap；可从队列取「未解决」任务 | `TaskWorkflow.current_assignee` + `stage`；普通成员在「下一任务」链路中被限制为自己名下的工作流任务 |
| **分配方式** | 无内置「按比例分给标注员」 | `ProjectTeamAllocation` 中 `label` 角色 + `allocation_percent`，分发时用 **最大余额法** 拆整数任务数 |
| **审核 / 验收** | 无一等公民模型 | `review` / `accept` 池 **轮询（round-robin）** 指定处理人；驳回回到 `annotate_user` |

结论：**工作流负责「业务流水线与责任人」；`is_labeled` / overlap 仍反映 LS 侧「标注份数是否凑齐」。** UI/API 已通过 `TaskSerializer.workflow` 字段提示勿把工作流阶段与 `is_labeled` 混为一谈。

## 2. 核心业务对象与关系（ER 语义）

```
Organization ──< Project ──< Task ────< Annotation (DB: task_completion)
                │              │
                │              └── 1:1 TaskWorkflow (启用工作流时)
                │
                ├── ProjectTeamAllocation (per user + role)
                ├── ProjectWorkflowSettings (1:1, round-robin 游标)
                └── …

Task ──< TaskLock (并发标注锁)
Task / Annotation ──< AnnotationDraft
```

- **Task**：一条业务样本；`overlap`、`total_annotations`、`cancelled_annotations`、`is_labeled` 等支撑原生队列与统计。
- **Annotation**：标注结果；物理表名为 **`task_completion`**（历史命名）。
- **TaskWorkflow**：每条 Task 至多一行（`OneToOne`，主键即 `task_id`），承载阶段与当前责任人。
- **ProjectTeamAllocation**：项目团队成员及角色；同一 `(project, user, role)` 唯一。

## 4. 任务工作流：阶段、字段与流转规则

### 4.1 阶段枚举 `TaskWorkflowStage`

- `annotate`：标注  
- `review`：审核（可选池）  
- `accept`：验收（可选池）  
- `done`：结束（`current_assignee` 置空）

### 4.2 `TaskWorkflow` 关键字段

- **`annotate_user`**：该任务的标注责任人；**驳回**时回到此人。  
- **`current_assignee`**：当前阶段必须由谁处理（`done` 时为 `NULL`）。  
- **`stage`**：当前阶段。

### 4.3 初始化：分发 `distribute_tasks_for_project`

入口：`POST /api/projects/<pk>/workflow/distribute/`（`workflow_services.distribute_tasks_for_project`）。

1. 若 `task_workflow_enabled` 为假，会置真并保存。  
2. 读取所有 `role=label` 的 `ProjectTeamAllocation`，`allocation_percent` 作为权重；权重和须 **> 0**。  
3. 对「尚无 `TaskWorkflow` 行」的任务按 `id` 排序，用 **`allocate_integer_slots`**（最大余额法）分配名额，创建行：  
   - `stage=annotate`  
   - `annotate_user_id` = 分配到的用户  
   - `current_assignee_id` = 同上  

### 4.4 标注提交后前进：`submit_annotation_after_labeling`

触发方式（双重保险）：

1. **API**：`POST /api/tasks/<pk>/workflow/submit-annotation/`  
2. **Signal**：`tasks.models.advance_task_workflow_after_annotation_saved` —— 在标注 **创建** 且非 skip、`stage==annotate`、提交者为当前责任人时，`transaction.on_commit` 调用同一套逻辑。

**校验要点**：

- 项目开启工作流；当前 `stage` 为 `annotate`。  
- `current_assignee_id == user.id`。  
- 至少存在一条 **`was_cancelled=False`** 且 **`completed_by=user`** 的 `Annotation`。

**流转**：

- 若配置了 **review 池**：`pick_next_round_robin(project, REVIEW)` → `stage=review`，`current_assignee=该校审核员`。  
- 否则若有 **accept 池**：直接进入 `accept`。  
- 若两池皆空：**`_mark_task_done`** —— `stage=done`，`current_assignee=None`，必要时 **`task.is_labeled=True`**。

### 4.5 审核：`review_decision(task_id, user, approve)`

- 非 `review` 或非当前审核员 → 校验失败。  
- **`approve=False`**：`stage=annotate`，`current_assignee=annotate_user`（返工）。  
- **`approve=True`**：若有 accept 池则轮询指定验收人；否则直接 `_mark_task_done`。

### 4.6 验收：`accept_decision(task_id, user, approve)`

- **`approve=False`**：退回 **annotate / annotate_user**。  
- **`approve=True`**：**`_mark_task_done`**。

### 4.7 Round-robin：`pick_next_round_robin`

- 使用 **`project_workflow_settings`** 中 **`rr_review_index` / `rr_accept_index`**（`select_for_update` 防止并发游标错乱）。  
- 池内用户按 **`user_id` 排序** 后取模轮询。

## 5. 权限、可见性与「谁能看到哪些任务」

### 5.1 项目列表可见性 `apply_project_team_visibility`

- 项目 **没有任何** `ProjectTeamAllocation`：**组织内成员**可见（兼容旧行为）。  
- 一旦有分配行：仅 **创建者** 或 **任意角色在本项目上有一条 allocation** 的用户可见；**组织 owner / superuser** 看全部。

### 5.2 任务列表范围 `Task.objects.for_user`

在「组织 + 可见项目」基础上，对工作流项目追加：

- **`task_workflow_enabled=False`**：项目中任务照常（仍受组织与可见项目约束）。  
- **`task_workflow_enabled=True`**：普通成员 **仅能拿到「自己是 `current_assignee`」或自己是创建者 / admin 角色分配」相关的任务**（实现见 `data_manager/managers.py` 中 `TaskManager.for_user`）。

超级用户、组织 owner、**项目创建者**、**`user_can_manage_project`**（创建者 / admin 分配 / 组织 owner）在 **`get_next_task`** 里还会 **绕过「仅本人工作流任务」限制**，以便管理端浏览全量任务。

### 5.3 创建标注时的硬性校验 `tasks.api.AnnotationsListAPI.perform_create`

若 `task_workflow_enabled`：

- 无 `TaskWorkflow` → **禁止标注**（提示需先分发）。  
- `stage != annotate` → **禁止继续标注**。  
- `current_assignee` 不是当前用户 → **禁止标注**。

## 6. Label Stream / 「下一任务」与原生队列逻辑（与工作流的衔接）

核心函数：`projects.functions.next_task.get_next_task`。

1. **`_restrict_prepared_tasks_for_workflow`**：对工作流项目，把候选任务限制为 **`workflow.current_assignee=self` 且 `stage in (annotate, review, accept)`**（管理角色等除外）。  
2. **`get_not_solved_tasks_qs`**：基于用户是否已对该任务提交过 **annotation**（及 postpone draft、skip_queue、overlap、GT、低一致性策略等）筛选「未解决」任务。  
3. 再结合 **Ground-truth 优先**、**breadth-first**、**sampling（顺序 / 均匀 / 不确定度）**、**skipped / postponed 队列** 等选取下一任务。  
4. **`TaskLock`**：在并发场景限制同一任务被多人同时标注（与工作流并行存在）。

## 7. FSM（有限状态管理）在代码中的位置

- **基类**：`fsm.models.FsmHistoryStateModel` —— 在 `save()` 后根据注册的 transition 写入状态轨迹（受 **CurrentContext / feature flag** 等控制）。  
- **参与模型**：如 `Task`、`Annotation`、`TaskLock`、`AnnotationDraft`、`Project` 等继承或混入 FSM。  
- **注册的状态模型**：`fsm/state_models.py` 中 `TaskState`、`AnnotationState`、`ProjectState`。

工程上可把 **FSM** 理解为「横切的审计与生命周期状态」，把 **`task_workflow`** 理解为「纵切的业务岗位流水线」。

## 9. 与工作流相关的主要 HTTP API

| 方法 | 路径（前缀依部署而定） | 说明 |
|------|------------------------|------|
| GET/POST | `/api/projects/<pk>/workflow/team/` | 列出 /  upsert 团队成员与角色 |
| DELETE | `/api/projects/<pk>/workflow/team/<allocation_id>/` | 删除一条分配 |
| POST | `/api/projects/<pk>/workflow/distribute/` | 为无工作流的任务批量创建 `TaskWorkflow` |
| GET | `/api/projects/<pk>/workflow/my-tasks/?stage=annotate|review|accept` | 当前用户在某阶段的任务列表 |
| GET | `/api/tasks/<pk>/workflow/` | 查询该任务工作流摘要 |
| POST | `/api/tasks/<pk>/workflow/submit-annotation/` | 标注完成后推进阶段 |
| POST | `/api/tasks/<pk>/workflow/review/` | body: `{ "approve": bool }` |
| POST | `/api/tasks/<pk>/workflow/accept/` | body: `{ "approve": bool }` |

（权限类使用 `projects_change` / `tasks_change` 等，详见 `workflow_api.py`、`tasks/urls.py`。）

## 10. 端到端流程（建议对照联调）

1. **创建项目** → 创建者写入 `project_team_allocation`（admin）。  
2. **配置团队**：为标注员添加 `label` + 百分比；按需添加 `review` / `accept` / `admin`。  
3. **导入任务** → `task` 表增量。  
4. **分发**：`distribute` → 写入 **`task_workflow`**（annotate + 责任人）。  
5. **标注员**打开 Label Stream / DM：**仅能命中分配给自己的 annotate 任务**；提交 annotation。  
6. **自动或手动** `submit-annotation`：**signal + API** 推动到 review/accept/done。  
7. **审核 / 验收** 轮询到人；**驳回**回到 **`annotate_user`**。  
8. **验收通过** → `done`，必要时 **`task.is_labeled=True`**。
