---

本文基于当前 Label Studio 二开任务流转代码审阅结果，给出可执行的修复方案。重点解决以下核心风险：

1. 原生 annotation 接口可绕过 workflow 当前处理人校验。
2. 审核/验收驳回后，旧 annotation 可再次满足提交条件。
3. `Task.is_labeled` 与 `TaskWorkflow.stage` 不一致。
4. 标注保存后的 workflow 推进存在 signal 与前端显式 POST 双入口冲突。
5. 我的任务分页、任务分发并发、比例校验、跨组织配置和审核/验收语义不清等稳定性问题。

## 1. 修复目标

### 1.1 业务目标

修复完成后，workflow 项目应满足以下行为：

| 场景 | 目标行为 |
| --- | --- |
| 任务分发 | 只能把未进入 workflow 的任务分发给合法标注员；并发重复分发不产生脏数据或 500 异常 |
| 标注阶段 | 只有当前标注处理人可以创建、更新、删除自己的标注结果 |
| 审核阶段 | 只有当前审核人可以审核通过或驳回；默认不允许审核人直接修改标注内容 |
| 验收阶段 | 只有当前验收人可以验收通过或驳回；默认不允许验收人直接修改标注内容 |
| 驳回返工 | 驳回必须绑定具体 annotation 版本；标注员必须新增或更新标注后才能再次提交 |
| 完成态 | workflow 项目的整单完成态以 `TaskWorkflow.stage = done` 为准，`Task.is_labeled` 与其保持一致 |
| 我的任务 | 支持服务端分页，超过 100 条待办时可以完整翻页 |
| 审计 | 可追踪每次提交、审核、验收、驳回的操作人、时间、annotation 和意见 |

### 1.2 技术目标

1. 将 workflow 权限判断集中到后端，前端只做交互约束，不作为安全边界。
2. 将 workflow 状态变更封装到 service 层，禁止在 API、signal、前端回调中重复实现状态推进逻辑。
3. 将 annotation 内容修改和 workflow 决策分离，避免 reviewer/acceptor 通过原生 annotation API 改动标注结果。
4. 对关键 service 补自动化测试，确保后续迭代不会回归。

## 2. 总体修复策略

建议按四个阶段交付，优先先堵安全和质量闭环漏洞，再统一状态、接口和前端体验。

| 阶段 | 优先级 | 范围 | 交付结果 |
| --- | --- | --- | --- |
| 第一阶段 | P0 | annotation 权限、驳回返工版本、审计记录、`is_labeled` 回退 | 防止越权修改和旧版本重复提交 |
| 第二阶段 | P1 | 双推进幂等、我的任务分页、接口返回结构 | 提升接口一致性和待办完整性 |
| 第三阶段 | P2 | 分发事务、比例校验、跨组织策略、前端模式区分 | 提升配置与管理端可靠性 |
| 第四阶段 | P2 | 自动化测试、数据修复脚本、上线检查 | 提供回归保护和历史数据治理 |

## 3. 数据模型调整

### 3.1 `TaskWorkflow` 增加当前提交版本字段

文件：`label_studio/projects/workflow_models.py`

建议在 `TaskWorkflow` 增加以下字段，用于记录当前正在被审核/验收的 annotation 版本和最近驳回状态。

| 字段 | 类型 | 允许空 | 用途 |
| --- | --- | --- | --- |
| `current_annotation` | `ForeignKey('tasks.Annotation', SET_NULL)` | 是 | 当前提交进入审核/验收的 annotation |
| `last_submitted_at` | `DateTimeField` | 是 | 最近一次标注员提交时间 |
| `last_rejected_at` | `DateTimeField` | 是 | 最近一次审核/验收驳回时间 |
| `last_rejected_by` | `ForeignKey(User, SET_NULL)` | 是 | 最近一次驳回人 |
| `last_rejected_annotation` | `ForeignKey('tasks.Annotation', SET_NULL)` | 是 | 最近被驳回的 annotation |
| `last_reject_reason` | `TextField` | 是 | 最近驳回原因，首期可选填 |

推荐模型形态：

```python
class TaskWorkflow(models.Model):
    # existing fields ...
    current_annotation = models.ForeignKey(
        'tasks.Annotation',
        on_delete=models.SET_NULL,
        null=True,
        blank=True,
        related_name='+',
        help_text='Annotation version currently under review/acceptance',
    )
    last_submitted_at = models.DateTimeField(null=True, blank=True)
    last_rejected_at = models.DateTimeField(null=True, blank=True)
    last_rejected_by = models.ForeignKey(
        settings.AUTH_USER_MODEL,
        on_delete=models.SET_NULL,
        null=True,
        blank=True,
        related_name='+',
    )
    last_rejected_annotation = models.ForeignKey(
        'tasks.Annotation',
        on_delete=models.SET_NULL,
        null=True,
        blank=True,
        related_name='+',
    )
    last_reject_reason = models.TextField(null=True, blank=True)
```

说明：

1. `current_annotation` 是 workflow 当前判定对象，审核和验收都围绕它处理。
2. `last_rejected_at` 用于返工校验：再次提交时，annotation 必须在该时间之后创建或更新。
3. 首期不建议直接改 `Annotation` 原模型增加状态字段，避免影响 Label Studio 原生语义；workflow 自己维护提交版本更稳妥。

### 3.2 新增 `TaskWorkflowAction` 审计表

文件：`label_studio/projects/workflow_models.py`

新增一张 history/action 表，记录所有 workflow 关键动作。该表既解决审计需求，也方便排查任务卡住原因。

建议字段：

| 字段 | 类型 | 用途 |
| --- | --- | --- |
| `id` | `BigAutoField` | 主键 |
| `workflow` | `ForeignKey(TaskWorkflow)` | 关联 workflow |
| `project` | `ForeignKey(Project)` | 冗余项目，便于查询 |
| `task` | `ForeignKey(Task)` | 冗余任务，便于查询 |
| `action` | `CharField` | `distribute` / `submit` / `review_approve` / `review_reject` / `accept_approve` / `accept_reject` / `reopen` |
| `stage_from` | `CharField` | 操作前阶段 |
| `stage_to` | `CharField` | 操作后阶段 |
| `actor` | `ForeignKey(User)` | 操作人，系统自动分发可为空 |
| `assignee_before` | `ForeignKey(User)` | 操作前当前处理人 |
| `assignee_after` | `ForeignKey(User)` | 操作后当前处理人 |
| `annotation` | `ForeignKey(Annotation)` | 本次提交/审核/验收针对的 annotation |
| `comment` | `TextField` | 审核/验收意见或驳回原因 |
| `metadata` | `JSONField` | 扩展信息，例如来源 `signal` / `api` |
| `created_at` | `DateTimeField` | 操作时间 |

推荐增加索引：

1. `(project, created_at)`：项目级审计列表。
2. `(task, created_at)`：单任务流转日志。
3. `(workflow, created_at)`：workflow 明细。
4. `(action, created_at)`：统计驳回率、通过率。

### 3.3 迁移文件建议

当前 projects migration 最新编号为 `0037_project_template_group.py`，建议新增：

1. `label_studio/projects/migrations/0038_task_workflow_revision_and_actions.py`

迁移内容：

1. 为 `task_workflow` 增加 `current_annotation_id`、`last_submitted_at`、`last_rejected_at`、`last_rejected_by_id`、`last_rejected_annotation_id`、`last_reject_reason`。
2. 创建 `task_workflow_action` 表。
3. 增加必要索引。

历史数据回填建议：

1. 对 `stage in ('review', 'accept', 'done')` 且 `current_annotation_id is null` 的 workflow，尝试取该任务下 `completed_by_id = annotate_user_id`、`was_cancelled = False` 的最新 annotation 作为 `current_annotation`。
2. `last_submitted_at` 可回填为 `current_annotation.updated_at`。
3. 无法找到 annotation 的 workflow 保持空值，并由数据检查脚本输出，交由人工处理。

## 4. 后端修复方案

### 4.1 收紧 Annotation 原生接口权限

涉及文件：

| 文件 | 改动点 |
| --- | --- |
| `label_studio/tasks/api.py` | `AnnotationAPI.get_queryset()`、`update()`、`delete()`、`AnnotationsListAPI.perform_create()` |
| `label_studio/tasks/models.py` | 必要时加强 `Annotation.has_permission()` |
| `label_studio/projects/workflow_services.py` | 增加 workflow 权限校验 helper |
| `label_studio/projects/access.py` | 如确认项目权限 stub 仍存在，补真实可见性约束 |

#### 4.1.1 Queryset 从全量改为用户可见

当前 `AnnotationAPI` 使用：

```python
queryset = Annotation.objects.all()
```

建议改为：

```python
def get_queryset(self):
    return Annotation.objects.for_user(self.request.user).select_related(
        'task', 'project', 'completed_by', 'task__workflow'
    )
```

效果：

1. 避免登录用户通过 annotation ID 访问不在自己可见项目内的数据。
2. 与 `AnnotationsListAPI.get_queryset()` 的 `Task.objects.for_user()` 策略保持一致。
3. 为后续对象级 workflow 校验提供基础。

#### 4.1.2 增加 workflow annotation 写权限校验

建议在 `projects/workflow_services.py` 或新增 `projects/workflow_permissions.py` 中集中实现：

```python
def assert_can_create_annotation_for_workflow(task, user):
    ...

def assert_can_update_annotation_for_workflow(annotation, user):
    ...

def assert_can_delete_annotation_for_workflow(annotation, user):
    ...
```

推荐规则：

| 操作 | 非 workflow 项目 | workflow annotate 阶段 | workflow review 阶段 | workflow accept 阶段 | workflow done 阶段 |
| --- | --- | --- | --- | --- | --- |
| 读取 annotation | 保持原规则 | 项目可见用户可读 | 当前 reviewer、当前 acceptor、项目管理员、原标注员可读 | 当前 acceptor、项目管理员、原标注员可读 | 项目可见用户可读或按产品限制 |
| 创建 annotation | 保持原规则 | 仅 `current_assignee` 可创建 | 禁止 | 禁止 | 禁止 |
| 更新 annotation 内容 | 保持原规则 | 仅 `current_assignee` 且 `completed_by = user` 可更新 | 过渡期：当前 reviewer 可保存当前 `current_annotation` 的审改，但必须严格限制 task、stage、assignee、annotation 和可写字段；完成后写 history 区分"审核时修改"与"标注时修改" | 默认禁止，必须走验收接口 | 禁止 |
| 删除 annotation | 保持原规则 | 仅 `current_assignee` 且 `completed_by = user` 可删除 | 禁止 | 禁止 | 禁止 |
| 审核/验收决策 | 不适用 | 不适用 | 仅 `current_assignee` 走 workflow review API | 仅 `current_assignee` 走 workflow accept API | 不适用 |

> **过渡期注意**：当前前端 `onAcceptAnnotation()`/`onRejectAnnotation()` 在调用审核/验收决策前会先通过 `persistReviewEditsIfDirty()` 对 annotation 做 PATCH（`lsf-sdk.js:872-893`）。如果立即禁止 reviewer 修改 annotation，审核-改稿-通过流程会断。首期过渡方案是：review 阶段允许当前 reviewer 通过现有 PATCH 保存当前任务的 `wf.current_annotation`，但必须校验 `stage=review`、`current_assignee=request.user`、`annotation.id=wf.current_annotation_id`，并限制不能改 `completed_by`、`task`、`project`、`ground_truth` 等归属和高权限字段，同时在 `TaskWorkflowAction` 中附记 "审核时修改了标注内容"。后续更稳妥的方案是让 review 决策接口携带 annotation diff，在同一个事务内完成保存和审核决策，再关闭 reviewer 的原生 PATCH 权限。

对象级校验要点：

1. `annotation.task.workflow.stage` 必须是 `annotate` 才允许普通标注员改内容。
2. `workflow.current_assignee_id == user.id`。
3. `annotation.completed_by_id == user.id`，防止当前标注员修改其他人的历史 annotation。
4. `PUT/PATCH` 中如果包含 `completed_by`，workflow 项目必须忽略或强制为当前用户，禁止伪造提交人。
5. `ground_truth` 等高权限字段不应由普通 workflow 标注员修改，建议限定项目管理员或原生管理员权限。

#### 4.1.3 创建 annotation 时强制当前用户

当前 `AnnotationsListAPI.perform_create()` 只有在 `completed_by` 不存在时才写入当前用户。workflow 项目中应强制覆盖：

```python
if getattr(task.project, 'task_workflow_enabled', False):
    extra_args['completed_by'] = self.request.user
elif 'completed_by' not in ser.validated_data:
    extra_args['completed_by'] = self.request.user
```

这样可以避免用户在 workflow 项目里通过请求体把 annotation 记到其他人名下。

#### 4.1.4 API 错误码建议

| 场景 | HTTP 状态 | 错误信息 |
| --- | --- | --- |
| 任务未分发 | `403` | `该任务尚未进入工作流，请先进行任务分发。` |
| 非当前处理人 | `403` | `该任务未分配给当前用户，不能修改标注。` |
| 非标注阶段改内容 | `403` | `该任务当前不在标注阶段，不能修改标注内容。` |
| 修改他人 annotation | `403` | `不能修改其他用户提交的标注。` |
| done 后修改 | `403` | `该任务流程已完成，不能继续修改标注。` |

#### 4.1.5 AnnotationDraft API 也需要 workflow 保护

当前 `AnnotationDraftListAPI` 和 `AnnotationDraftAPI`（`label_studio/tasks/api.py:685-716`）使用 `AnnotationDraft.objects.all()` 作为 queryset，没有任何 workflow 校验。非当前处理人或 reviewer/acceptor 可通过创建/修改草稿间接绕过 annotation 的保护。

建议改动：

1. **`AnnotationDraftListAPI.get_queryset()`**：改为 `AnnotationDraft.objects.filter(task_id=...)`（已有），但 `perform_create()` 需增加 workflow 校验——检查任务是否已分发、当前 stage 是否为 `annotate`、当前处理人是否为请求用户。
2. **`AnnotationDraftAPI.get_queryset()`**：改为按当前用户可见项目过滤，并增加 workflow 阶段校验（修改和删除草稿同样受 stage/assignee 限制）。
3. **`AnnotationDraftAPI.update()`/`delete()`**：增加与 `AnnotationAPI` 同等强度的 workflow 阶段和当前处理人校验。

> 注意：草稿和正式 annotation 的权限应保持一致，否则草稿会成为绕过 workflow 的旁路。例如 reviewer 通过创建草稿记录审改意见是合理需求，但 reviewer 使用草稿 API 修改原始标注数据则应被禁止。

### 4.2 修复驳回返工闭环

涉及文件：

| 文件 | 改动点 |
| --- | --- |
| `label_studio/projects/workflow_services.py` | `submit_annotation_after_labeling()`、`review_decision()`、`accept_decision()` |
| `label_studio/projects/workflow_api.py` | review/accept body 增加 `comment`，响应返回 workflow 版本字段 |
| `label_studio/projects/workflow_models.py` | 新增字段和 history 表 |

#### 4.2.1 提交时绑定最新有效 annotation

`submit_annotation_after_labeling(task_id, user)` 中不再只做 `.exists()` 判断，而是选出本次提交的 annotation：

```python
def _latest_valid_annotation_for_submit(wf, user):
    qs = Annotation.objects.filter(
        task_id=wf.task_id,
        completed_by_id=user.id,
        was_cancelled=False,
    ).order_by('-updated_at', '-id')

    if wf.last_rejected_at:
        qs = qs.filter(updated_at__gt=wf.last_rejected_at)

    return qs.first()
```

提交规则：

1. 首次提交：取当前用户最新一条未取消 annotation。
2. 驳回后再次提交：annotation 的 `updated_at` 必须晚于 `last_rejected_at`。
3. 如果没有满足条件的 annotation，返回 `400`：`驳回后请先更新或重新提交标注结果。`
4. 推进到 `review` / `accept` / `done` 前，写入 `wf.current_annotation` 和 `wf.last_submitted_at`。
5. 写入一条 `TaskWorkflowAction(action='submit')`。

#### 4.2.2 审核/验收必须针对当前 annotation

`review_decision()` 和 `accept_decision()` 开始时增加校验：

1. `wf.current_annotation_id` 不为空。
2. `wf.current_annotation.task_id == wf.task_id`。
3. 当前 annotation 未取消。

如果历史数据导致为空，可先允许进入兼容路径，但必须记录 warning 日志，并在数据检查脚本中输出。

#### 4.2.3 驳回时记录版本和意见

review reject：

```python
wf.stage = TaskWorkflowStage.ANNOTATE
wf.current_assignee_id = wf.annotate_user_id
wf.last_rejected_at = timezone.now()
wf.last_rejected_by = user
wf.last_rejected_annotation = wf.current_annotation
wf.last_reject_reason = comment
wf.save(update_fields=[...])
```

accept reject 同理。

同时写入 history：

| 动作 | `action` | `stage_from` | `stage_to` | `annotation` |
| --- | --- | --- | --- | --- |
| 审核驳回 | `review_reject` | `review` | `annotate` | `wf.current_annotation` |
| 验收驳回 | `accept_reject` | `accept` | `annotate` | `wf.current_annotation` |

注意：驳回时不要清空 `current_annotation`，它仍表示最近一次被驳回的版本。再次提交成功后再覆盖为新版本。

#### 4.2.4 通过时记录处理动作

review approve：

1. 写入 `TaskWorkflowAction(action='review_approve')`。
2. 如果有验收池，进入 `accept` 并分配验收人。
3. 如果无验收池，进入 `done`。

accept approve：

1. 写入 `TaskWorkflowAction(action='accept_approve')`。
2. 进入 `done`。
3. `task.is_labeled = True`。

### 4.3 统一 `is_labeled` 与 workflow 完成态

涉及文件：`label_studio/projects/workflow_services.py`

#### 4.3.1 增加统一回退方法

建议新增 helper：

```python
def _return_task_to_annotate(wf, *, rejected_by, comment, action):
    wf.stage = TaskWorkflowStage.ANNOTATE
    wf.current_assignee_id = wf.annotate_user_id
    wf.last_rejected_at = timezone.now()
    wf.last_rejected_by = rejected_by
    wf.last_rejected_annotation = wf.current_annotation
    wf.last_reject_reason = comment
    wf.save(update_fields=[...])

    task = wf.task
    if task.is_labeled:
        task.is_labeled = False
        task.save(update_fields=['is_labeled', 'updated_at'])
```

所有审核/验收驳回都走这个 helper，避免遗漏字段。

#### 4.3.2 明确完成态口径

后端内部规则：

1. workflow 项目：整单完成态以 `TaskWorkflow.stage == TaskWorkflowStage.DONE` 为准。
2. 非 workflow 项目：沿用原生 `Task.is_labeled`。
3. workflow 项目中，`is_labeled` 只作为兼容原生列表和统计的冗余字段，必须被 workflow service 同步维护。

#### 4.3.3 历史数据修复

新增管理命令建议：

文件：`label_studio/projects/management/commands/fix_task_workflow_consistency.py`

命令能力：

1. 默认 dry-run 输出异常数量。
2. `--apply` 时执行修复。
3. `--project-id` 支持按项目修复。
4. 输出 CSV 或日志，方便回滚核对。

修复规则：

| 异常 | 修复方式 |
| --- | --- |
| `workflow.stage != done` 且 `task.is_labeled = True` | 设置 `task.is_labeled = False` |
| `workflow.stage = done` 且 `task.is_labeled = False` | 设置 `task.is_labeled = True` |
| `workflow.stage = done` 且 `current_assignee_id is not null` | 设置 `current_assignee_id = null` |
| `workflow.stage != done` 且 `current_assignee_id is null` | 输出异常，人工指定处理人 |

### 4.4 修复标注保存双推进

涉及文件：

#### 4.4.1 推荐最终架构

### 4.6 分发逻辑增加事务和并发保护

涉及文件：`label_studio/projects/workflow_services.py`

#### 4.6.1 事务边界

`distribute_tasks_for_project(project)` 整体包进 `transaction.atomic()`：

```python
with transaction.atomic():
    project = Project.objects.select_for_update().get(pk=project.pk)
    settings, _ = ProjectWorkflowSettings.objects.select_for_update().get_or_create(project=project)
    ...
```

推荐锁项目行或 `ProjectWorkflowSettings` 行，确保同一项目同一时间只有一个分发过程。

#### 4.6.2 创建方式

建议使用 `bulk_create(ignore_conflicts=True)`，再按实际写入数量返回。

**数据库兼容性警告**：

| 数据库 | `bulk_create(ignore_conflicts=True)` 支持 |
|--------|------------------------------------------|
| PostgreSQL 9.5+ | 支持 `ON CONFLICT DO NOTHING`，但不要依赖返回对象数量计算 created |
| SQLite 3.24+ | Django 支持 `ON CONFLICT DO NOTHING`，仍建议重新查询统计 |
| MySQL / MariaDB | Django 会使用 `INSERT IGNORE`，不会抛 `NotSupportedError`；但可能把部分错误降级为 warning，且返回对象主键/数量不可靠 |

如果目标数据库包含 MySQL，且不希望 `INSERT IGNORE` 把非唯一冲突错误降级为 warning，可改用保守策略：

```python
for task in tasks:
    TaskWorkflow.objects.get_or_create(
        task=task,
        defaults={'project': project, 'stage': ..., 'annotate_user_id': uid, 'current_assignee_id': uid},
    )
```

注意：当前 `TaskWorkflow.task` 是 one-to-one primary key，不同数据库对 `ignore_conflicts` 的返回 created count 支持不完全一致。更稳妥的返回方式：

1. 分发前记录 `before_count = TaskWorkflow.objects.filter(project=project).count()`。
2. bulk create 后记录 `after_count`。
3. `created = after_count - before_count`。

#### 4.6.3 返回结构

当前只返回：

```json
{"created": 10}
```

建议扩展为：

```json
{
  "created": 10,
  "skipped_existing": 25,
  "total_tasks": 35,
  "workflow_total": 35
}
```

这样前端能明确知道本次是新增分发还是没有新任务。

### 4.7 分配比例后端校验

涉及文件：

| 文件 | 改动点 |
| --- | --- |
| `label_studio/projects/workflow_api.py` | `TeamAllocationWriteSerializer` 字段和 validate |
| `label_studio/projects/workflow_services.py` | 分发前再次校验 label pool |
| `label_studio/projects/workflow_models.py` | 可选增加 model validators |

#### 4.7.1 单条校验

`allocation_percent` 增加范围限制：

```python
allocation_percent = serializers.DecimalField(
    max_digits=6,
    decimal_places=2,
    min_value=Decimal('0'),
    max_value=Decimal('100'),
    default=0,
)
```

非 label 角色比例应在验证时给出明确反馈而非无声清零：

```python
def validate(self, attrs):
    if attrs['role'] != ProjectTeamRole.LABEL:
        if attrs.get('allocation_percent', Decimal('0')) != Decimal('0'):
            raise ValidationError(
                {'allocation_percent': '非标注(label)角色的分配比例将被忽略，请设置为 0。'}
            )
        attrs['allocation_percent'] = Decimal('0')
    return attrs
```

> **注意**：不要无声覆盖（silent override）。如果管理员给 reviewer 配置了 `allocation_percent=50`，接口无声改成 0 会导致配置者误以为生效。应给出明确的校验错误或至少 warn 提示。

#### 4.7.2 项目级总和校验

推荐规则：

1. label 角色总和必须等于 100，允许误差 `0.01`。
2. 至少有一个 label 用户比例大于 0。
3. 分发前再次调用校验，防止绕过 serializer 或历史脏数据。

如果产品希望“比例是权重，不要求总和 100”，则需要把 UI 文案从“百分比”改为“权重”，并禁止负数。当前字段名和帮助文本都是 percent，推荐采用“总和等于 100”的规则。

### 4.8 跨组织人员配置策略

涉及文件：

| 文件 | 改动点 |
| --- | --- |
| `label_studio/projects/workflow_api.py` | 人员配置时校验用户是否属于项目 organization |

#### 4.8.1 推荐短期策略：禁止跨组织配置

当前代码允许跨组织人员加入项目团队，但项目、任务、annotation 可见性仍按 `active_organization` 过滤，这会导致配置成功但用户看不到任务。

短期建议明确规则：项目团队成员必须属于项目 organization。

人员配置时增加校验：

```python
from organizations.models import OrganizationMember

user = get_object_or_404(User, pk=uid)
if not OrganizationMember.objects.filter(
    user=user,
    organization_id=project.organization_id,
    deleted_at__isnull=True,
).exists():
    raise ValidationError('用户不属于当前项目组织，不能加入项目团队。')
```

> **注意**：不能只看 `user.active_organization`，也不能忽略软删除成员关系。用户-组织关系通过 `organizations.models.OrganizationMember` 中间表管理，校验必须走这个表并带上 `deleted_at__isnull=True`。

#### 4.8.2 如必须支持跨组织协作

如果产品确实要求跨组织协作，则不能只改配置接口，必须同步调整：

1. `Project.objects.for_user(user)`：除了 active organization 项目，还应包含显式分配给该用户的项目。
2. `Task.objects.for_user(user)`：显式团队项目中的任务可见，但 workflow 项目仍只返回当前处理人任务或管理员任务。
3. `Annotation.objects.for_user(user)`：显式团队项目中的 annotation 可读范围按角色限制。
4. `_visible_org_project()` / `_visible_org_task()`：不能只用 `request.user.active_organization` 过滤。
5. UI 需要明确跨组织项目入口，避免用户因 active organization 不匹配看不到页面。

该方案改动面更大，建议单独立项；本次修复优先采用“禁止跨组织配置”。

## 6. 数据修复与上线步骤

### 6.1 上线前检查

上线前执行 dry-run 数据检查，输出以下异常：

1. `TaskWorkflow.stage != 'done'` 但 `Task.is_labeled = True`。
2. `TaskWorkflow.stage = 'done'` 但 `Task.is_labeled = False`。
3. `TaskWorkflow.stage != 'done'` 但 `current_assignee_id is null`。
4. `TaskWorkflow.stage = 'review'` 但项目没有 review 角色。
5. `TaskWorkflow.stage = 'accept'` 但项目没有 accept 角色。
6. `TaskWorkflow.current_assignee_id` 不在当前阶段对应角色池中。
7. label 角色比例总和不等于 100。
8. label 角色存在负数或大于 100 的比例。
9. 团队成员不属于项目 organization。
10. `stage in ('review', 'accept', 'done')` 但找不到可回填的 annotation。

### 6.2 推荐发布顺序

1. 发布数据库 migration。
2. 发布后端 service、API 权限和幂等修复（标注权限收紧可通过 feature flag 灰度/回滚，但 P0 验收时必须开启）。

4. 对明显一致性问题执行 `--apply` 修复。
5. 发布前端分页、SDK 和人员配置页修复。
6. 内部验证通过后，逐步对 workflow 项目开启严格权限和驳回返工 feature flag。
7. 观察 workflow API 错误率、驳回后再次提交成功率、分发接口错误率。
8. 一周后再考虑开启更严格规则，例如驳回原因必填、done 阶段 annotation 只读。

#### 6.2.1 Feature Flag 灰度策略

annotation 权限收紧对 workflow 项目的用户体验影响较大（尤其是 §4.1.2 的更新/删除限制），建议通过 feature flag 控制：

| Flag | 控制内容 | 发布策略 |
|------|---------|--------|
| `fflag_workflow_strict_annotation_perms` | 是否对 workflow 项目启用 annotation update/delete 的 stage/assignee 校验 | 可灰度开启；P0 验收必须开启，稳定后默认开启或移除 flag |
| `fflag_workflow_strict_draft_perms` | 是否对 workflow 项目启用 annotation draft 的 stage/assignee 校验 | 可灰度开启；P0/P1 验收必须开启，稳定后默认开启或移除 flag |
| `fflag_workflow_require_revision_after_reject` | 驳回后是否要求 annotation 更新晚于驳回时间 | 可灰度开启；P0 验收必须开启，不能长期允许旧版本再次提交 |

灰度建议：

1. 第一步：仅开启 `workflow_strict_annotation_perms`，观察 annotation update/delete 被拦截的请求中是否有正常业务流量。
2. 第二步：开启 `workflow_strict_draft_perms`。
3. 第三步：开启 `workflow_require_revision_after_reject`，确保驳回返工闭环。
4. 稳定两周后，将 flag 默认值改为 `true` 或直接移除 flag。

> 注意：feature flag 只作为灰度和回滚手段，不能作为长期默认关闭策略。否则 annotation 越权和驳回后旧版本再次提交这两个 P0 问题仍然存在。

> 注意：非 workflow 项目（`task_workflow_enabled=False`）不受这些 flag 影响，始终保持原行为。

### 6.3 回滚策略

如果发布后发现异常：

1. 数据库新增字段和表可以保留，不影响旧代码读取。
2. 后端权限修复如造成误拦截，可临时通过 feature flag 放宽 annotation update/delete，但不建议直接回滚 migration。
3. 前端移除显式 submit 后，如果 signal 推进异常，可临时恢复调用；由于后端 submit 已幂等，不会重新引入双推进报错。
4. 数据修复命令必须先 dry-run，并记录修复前 task/workflow id，必要时按日志反向恢复。

## 8. 关键实现细节

### 8.1 workflow service 状态变更必须加事务

以下函数建议都使用 `transaction.atomic()` 并锁定 workflow 行：

1. `submit_annotation_after_labeling()`
2. `review_decision()`
3. `accept_decision()`
4. `distribute_tasks_for_project()`

获取 workflow 时使用：

```python
TaskWorkflow.objects.select_for_update().select_related(...).get(task_id=task_id)
```

> **关键约束**：`select_for_update()` 必须在 `transaction.atomic()` 事务块内调用，否则 Django 会抛出 `TransactionManagementError`。当前 `get_task_workflow_or_404()`（`workflow_services.py:140-144`）在非事务上下文中被调用，改用 `select_for_update` 版本前**必须确保所有调用方已被 `transaction.atomic()` 包裹**。建议新增独立函数 `get_task_workflow_for_update(task_id)` 供事务内使用，保留原 `get_task_workflow_or_404()` 供只读查询使用。

避免同一任务被重复提交、重复审核或审核/验收请求并发覆盖。

### 8.2 round-robin 分配保持独立锁

`pick_next_round_robin()` 当前已经锁 `ProjectWorkflowSettings`。如果外层 service 已经处于事务中，应避免嵌套事务造成逻辑分散。建议拆成两个方法：

1. `_pick_next_round_robin_locked(project, role)`：要求调用方已在事务中，内部锁 settings 并递增游标。
2. `pick_next_round_robin(project, role)`：兼容外部调用，自己开事务。

workflow transition service 使用 locked 版本。

### 8.3 history 写入应与状态变更同事务

`TaskWorkflowAction` 必须和 `TaskWorkflow` 更新在同一个事务内写入。不能先改 workflow 再异步写 history，否则排查时会出现状态有变更但无记录。

### 8.4 API 响应统一

workflow transition API 建议统一返回：

```json
{
  "task_id": 1,
  "stage": "review",
  "current_assignee_id": 2,
  "annotate_user_id": 3,
  "current_annotation_id": 4,
  "last_submitted_at": "2026-05-15T10:00:00+08:00",
  "last_rejected_at": null,
  "already_submitted": false
}
```

前端所有 workflow 状态刷新都基于这个响应，不再自己推断。

### 8.5 保留兼容但收紧默认行为

由于当前系统是叠加在 Label Studio 原生 annotation/task 机制之上，修复时要注意兼容：

1. 非 workflow 项目尽量保持原行为。
2. workflow 项目才启用新增权限和版本校验。
3. 新字段允许为空，避免历史数据 migration 阻塞上线。
4. 强约束先在 service/API 层实现，数据库硬约束后续再逐步补充。

## 10. 风险与注意事项

1. `AnnotationAPI.get_queryset()` 收紧后，可能暴露历史上依赖全量 annotation ID 访问的内部脚本，需要提前排查。
2. 驳回后要求 annotation `updated_at > last_rejected_at`，如果数据库时间精度较低，极端情况下同一秒内更新可能误判；可使用 `id > last_rejected_annotation_id` 作为补充条件，或记录 `last_rejected_annotation.updated_at` 后要求 `updated_at >= last_rejected_at and id != last_rejected_annotation_id`。
3. 如果允许更新原 annotation 而不是新建 annotation，要确保 PATCH 确实触发 `updated_at` 更新。
4. 前端移除显式 submit 后，必须确认所有保存路径都会触发后端 signal；若存在 bulk create 或特殊导入路径，应明确是否需要进入 workflow。已知会绕过 `post_save` signal 的路径包括：

   - **`Annotation.objects.bulk_create()`**（`tasks/models.py:612-616`）：触发 `pre_bulk_create`/`post_bulk_create` 自定义信号，但**不会**触发 Django 的 `post_save`，因此不会自动推进 workflow。如果 workflow 项目使用 bulk import annotations，需要为 `post_bulk_create` 增加 workflow 推进逻辑。
   - **数据导入 API**（`/api/projects/:id/import` 等批量导入标注路径）：标注结果可能在导入时直接写入，不走标注保存的 signal 流程。
   - **直接 SQL 写入**：通过管理命令、脚本或数据库直连修改 annotation 表，完全不触发任何 Django signal。
   - **旧版 SDK 或第三方客户端**：可能不调用 workflow submit API，仅通过 annotation API 创建标注。

   建议对 workflow 项目增加定时任务或手动命令，定期检查 `stage = annotate` 但存在有效 annotation 的 workflow，自动推进或输出异常列表。
5. 数据修复命令必须先 dry-run，尤其是 `is_labeled` 回退会影响原生统计。
6. 跨组织协作如果后续要支持，改动会扩展到 Project/Task/Annotation 的 `for_user()`，不能只放开人员配置。

## 12. 结论

本次修复的关键不是单点修补某个接口，而是把 workflow 从“附加状态表”收束为真正的任务处理边界：谁能改 annotation、什么时候能推进、审核/验收针对哪个版本、完成态如何判断，都必须由后端 workflow service 统一决定。

优先建议先完成 P0 范围：annotation 写权限收口、返工版本绑定、history 审计和 `is_labeled` 回退。这部分直接影响数据安全和质量闭环。随后再处理双推进、分页、分发并发和配置一致性问题，最终补齐自动化测试和数据修复脚本。
