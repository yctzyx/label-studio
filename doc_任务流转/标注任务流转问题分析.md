# 标注任务流转问题分析

分析日期：2026-05-15

本文记录当前基于 Label Studio 二开的任务人员分配、标注、审核、验收流程代码审阅结论，重点覆盖任务分发后的流转链路、状态字段、权限边界、前后端协作方式以及已发现的潜在 bug。

## 2. 当前流程梳理

### 2.1 人员角色

`ProjectTeamRole` 定义了 4 类角色：

| 角色 | 值 | 用途 |
| --- | --- | --- |
| 标注人员 | `label` | 参与任务分发，使用 `allocation_percent` 决定分发比例 |
| 审核人员 | `review` | 任务标注完成后进入审核池，按轮询分配 |
| 验收人员 | `accept` | 审核通过后进入验收池，按轮询分配 |
| 项目管理员 | `admin` | 可管理项目团队和执行任务分发 |

人员配置表为 `project_team_allocation`，约束为同一项目、同一用户、同一角色唯一。一个用户可以同时拥有多个角色。

### 2.2 任务阶段

`TaskWorkflowStage` 定义了 4 个阶段：

| 阶段 | 含义 |
| --- | --- |
| `annotate` | 等待标注人员处理 |
| `review` | 等待审核人员处理 |
| `accept` | 等待验收人员处理 |
| `done` | 流程完成 |

每个进入工作流的任务会有一条 `task_workflow` 记录，关键字段如下：

| 字段 | 含义 |
| --- | --- |
| `task_id` | 任务 ID，一对一主键 |
| `project_id` | 项目 ID |
| `stage` | 当前阶段 |
| `annotate_user_id` | 原始标注人员，驳回时退回此人 |
| `current_assignee_id` | 当前阶段需要处理的人，完成后为空 |

### 2.3 分发逻辑

入口：`POST /api/projects/:id/workflow/distribute/`

实现：`distribute_tasks_for_project(project)`

当前逻辑：

1. 如果项目未启用 `task_workflow_enabled`，自动置为 `True`。
2. 查询项目内 `label` 角色人员。
3. 使用 `allocation_percent` 作为权重，通过 largest remainder 算法把未分发任务拆成整数份额。
4. 按任务 ID 升序，为每个没有 workflow 记录的任务创建 `TaskWorkflow`。
5. 初始阶段为 `annotate`，`annotate_user` 和 `current_assignee` 都为被分配到的标注员。

注意：分发只会处理没有 workflow 记录的任务，已经分发过的任务不会因为人员比例变化而重新分配。

### 2.4 标注后流转

入口有两处：

1. 后端 annotation 创建后的 `post_save` signal：`advance_task_workflow_after_annotation_saved()`。
2. 前端标注保存成功后调用：`POST /api/tasks/:id/workflow/submit-annotation/`。

实现：`submit_annotation_after_labeling(task_id, user)`

当前逻辑：

1. 检查项目已启用 workflow。
2. 检查任务当前阶段必须是 `annotate`。
3. 检查当前处理人必须是提交用户。
4. 检查该用户至少有一条未取消 annotation。
5. 如果有审核池，进入 `review`，审核人按轮询分配。
6. 如果没有审核池但有验收池，进入 `accept`，验收人按轮询分配。
7. 如果审核池和验收池都为空，直接进入 `done`。

### 2.5 审核流转

入口：`POST /api/tasks/:id/workflow/review/`

实现：`review_decision(task_id, user, approve)`

当前逻辑：

1. 检查当前阶段必须是 `review`。
2. 检查当前处理人必须是请求用户。
3. 审核驳回时，阶段退回 `annotate`，处理人退回 `annotate_user`。
4. 审核通过时，如果有验收池，进入 `accept`。
5. 审核通过时，如果没有验收池，直接进入 `done`。

### 2.6 验收流转

入口：`POST /api/tasks/:id/workflow/accept/`

实现：`accept_decision(task_id, user, approve)`

当前逻辑：

1. 检查当前阶段必须是 `accept`。
2. 检查当前处理人必须是请求用户。
3. 验收驳回时，阶段退回 `annotate`，处理人退回 `annotate_user`。
4. 验收通过时，阶段进入 `done`，`current_assignee` 置空，并设置 `task.is_labeled = True`。

### 2.7 我的任务

入口：`GET /api/projects/:id/workflow/my-tasks/?stage=annotate|review|accept`

实现：`queryset_my_tasks(project, user, stage)`

当前逻辑：

只返回当前项目下，指定阶段，并且 `workflow.current_assignee_id == request.user.id` 的任务。

## 3. 已发现问题

### 问题 1：annotation 原生接口权限过宽，可绕过 workflow 当前处理人校验

严重级别：严重

相关代码：

- `label_studio/tasks/api.py:449`，`AnnotationAPI`
- `label_studio/tasks/api.py:459`，`queryset = Annotation.objects.all()`
- `label_studio/tasks/models.py:763`，`Annotation.has_permission()`
- `label_studio/projects/mixins.py:74`，`ProjectMixin.has_permission()`
- `label_studio/core/permissions.py:84`，所有 permission 注册为 `rules.is_authenticated`

现象：

workflow 决策接口，例如审核、验收接口，会严格校验当前 stage 和当前处理人。但原有 annotation 更新、删除接口没有绑定 workflow 当前阶段和当前处理人。`AnnotationAPI` 的 queryset 是全量 annotation，最终对象权限只落到 `annotation.project.has_permission(user)`。当前 `ProjectMixin.has_permission()` 是 stub，直接返回 `True`。

> **补充说明**：annotation 的**创建**路径（`AnnotationsListAPI.perform_create()`，`label_studio/tasks/api.py:613-623`）已经做了 workflow 校验——检查项目是否启用 workflow、当前 stage 是否为 `annotate`、当前处理人是否为请求用户。因此创建操作是受保护的。但 **更新和删除**路径（`AnnotationAPI.update()` / `AnnotationAPI.delete()`）完全没有任何 workflow 校验，攻击面集中在这两条路径上。

风险：

1. 非当前处理人可能直接 PATCH 某个 annotation。
2. 审核人员或验收人员可能修改并非自己当前待处理任务的 annotation。
3. 如果知道 annotation ID，已登录用户存在跨项目访问风险，具体取决于全局 DRF 对象权限是否被调用以及项目权限是否被二开覆盖。
4. workflow 状态看似受控，但底层标注数据可以通过原生接口绕开流转约束。

建议修复：

1. `AnnotationAPI.get_queryset()` 改为 `Annotation.objects.for_user(request.user)`，至少限制到当前用户可见项目。
2. 对 workflow 项目增加对象级校验：
   - `annotate` 阶段：只有 `workflow.current_assignee` 可创建或更新自己的标注。
   - `review` 阶段：只有当前 reviewer 可执行审核相关修改。
   - `accept` 阶段：只有当前 acceptor 可执行验收相关修改。
   - `done` 阶段：普通角色不允许继续修改。
3. 区分“修改 annotation 内容”和“审核/验收决策”，避免 reviewer/acceptor 任意改原始标注。
4. 给 `Project.has_permission()` 或对象权限补上真实的组织、项目团队、角色约束。

### 问题 2：标注保存后存在双推进，signal 与前端显式 POST 冲突

严重级别：中高

相关代码：

- `label_studio/tasks/models.py:1478`，`advance_task_workflow_after_annotation_saved()`
- `label_studio/tasks/models.py:1516`，signal 调用 `submit_annotation_after_labeling()`
- `web/libs/datamanager/src/sdk/lsf-sdk.js:922`，`onSubmitAnnotation()`
- `web/libs/datamanager/src/sdk/lsf-sdk.js:952`，前端保存成功后调用 `maybeAdvanceTaskWorkflowAfterLabeling()`
- `web/libs/datamanager/src/sdk/lsf-sdk.js:767`，`maybeAdvanceTaskWorkflowAfterLabeling()`

现象：

annotation 创建成功后，后端 signal 会在事务提交后自动推进 workflow。前端在收到保存成功响应后，又会调用 `POST /api/tasks/:id/workflow/submit-annotation/`。如果 signal 已经先把任务从 `annotate` 推到 `review` 或 `accept`，前端这次 POST 会收到 “Task is not in annotate stage”。目前 SDK 通过 `errorHandlerSwallowWorkflow` 把错误吞掉，只在 console 打 warning。

风险：

1. API 行为不幂等，重复调用会报错。
2. 前端吞错会掩盖真实的 workflow 推进失败。
3. 第三方客户端或脚本若调用 annotation 创建后再显式提交 workflow，可能收到失败结果，误以为标注未完成。
4. 如果 signal 和前端请求时序不同，排查线上问题会比较困难。

建议修复：

1. 二选一保留推进来源：建议后端 signal 作为唯一推进入口，前端不再显式调用 submit-annotation。
2. 如果必须保留前端调用，则 `submit_annotation_after_labeling()` 应设计为幂等：当前任务已经不在 `annotate`，且已有当前用户 annotation 时，返回当前 workflow 状态而不是报错。
3. 前端不要无条件吞掉 workflow 错误，应区分“已推进”与“真实失败”。

### 问题 3：驳回后未绑定具体 annotation，再提交可被旧 annotation 满足

严重级别：严重

相关代码：

- `label_studio/projects/workflow_services.py:158`，`submit_annotation_after_labeling()`
- `label_studio/projects/workflow_services.py:197`，`review_decision()`
- `label_studio/projects/workflow_services.py:222`，`accept_decision()`

现象：

审核或验收驳回时，只是把 workflow stage 改回 `annotate`，处理人改回原标注员，没有记录被驳回的是哪条 annotation，也没有标记 annotation 为 rejected。再次提交时，`submit_annotation_after_labeling()` 只检查该用户是否存在任意未取消 annotation：

```python
Annotation.objects.filter(
    task_id=task_id,
    completed_by_id=user.id,
    was_cancelled=False,
).exists()
```

因此，即使标注员没有修改、没有新增 annotation，只要旧 annotation 还存在，就可能再次满足提交条件并推进到审核/验收。

风险：

1. 驳回不能强制返工。
2. 标注员可通过接口直接重新推进，不产生新的修订记录。
3. 审核/验收无法区分本次处理的是返工后的版本还是旧版本。
4. 质量闭环不可靠。

建议修复：

1. `TaskWorkflow` 增加当前 annotation/version 字段，例如 `current_annotation_id`、`rejected_annotation_id`、`last_submitted_at`。
2. 驳回时记录驳回原因、驳回人、驳回时间、目标 annotation。
3. 再次提交时要求 annotation 的 `updated_at` 或新建时间晚于驳回时间。
4. 或引入单独的 workflow history/review record 表，记录每次提交、审核、验收、驳回。

### 问题 4：`task.is_labeled` 与 workflow stage 不一致

严重级别：中高

相关代码：

- `label_studio/projects/workflow_services.py:148`，`_mark_task_done()`
- `label_studio/projects/workflow_services.py:204`，审核驳回只改 workflow，不改 `is_labeled`
- `label_studio/projects/workflow_services.py:229`，验收驳回只改 workflow，不改 `is_labeled`
- `web/apps/labelstudio/src/pages/MyTasks/MyTasksPage.jsx:37`，前端已用 workflow stage 判断完成

现象：

workflow 完成时，`_mark_task_done()` 会强制设置 `task.is_labeled = True`。但审核或验收驳回时，只把 stage 退回 `annotate`，没有把 `task.is_labeled` 改回 false。前端“我的任务”已经特别处理：workflow 项目的整单完成以 `workflow.stage === 'done'` 为准，而不是 `is_labeled`。

风险：

1. 原生 Data Manager 或统计仍可能把驳回任务视为已标注完成。
2. 原生 next task 逻辑、项目进度、导出筛选可能出现与 workflow stage 不一致的结果。
3. 用户在不同页面看到的完成数不一致。

建议修复：

1. workflow 项目中，业务完成态统一以 `TaskWorkflow.stage` 为准。
2. 审核/验收驳回时同步更新 `task.is_labeled = False`，或者避免 workflow 项目继续使用 `is_labeled` 表达整单完成。
3. 项目统计、任务列表、导出筛选统一接入 workflow stage。
4. 增加数据修复脚本，修正 `stage != done` 但 `is_labeled = True` 的历史数据。

### 问题 5：任务分发缺少事务和并发保护

严重级别：中

相关代码：

- `label_studio/projects/workflow_services.py:49`，`distribute_tasks_for_project()`
- `label_studio/projects/workflow_models.py:61`，`TaskWorkflow.task` 一对一主键

现象：

分发逻辑先查询已有 workflow，再查询未分发任务，随后逐条 `TaskWorkflow.objects.create()`。整个过程没有 `transaction.atomic()`，也没有对项目或任务加锁。

风险：

1. 两个管理员同时点击“分发任务”时，可能同时读取到同一批未分发任务。
2. 后提交的一方可能因为 one-to-one 唯一约束抛出 IntegrityError。
3. 部分任务可能已创建 workflow，部分任务失败，API 返回异常但数据已部分变更。
4. 前端无法明确知道哪些任务分发成功。

建议修复：

1. `distribute_tasks_for_project()` 使用 `transaction.atomic()`。
2. 对项目 workflow settings 或项目行加锁，确保同一项目同一时间只有一个分发过程。
3. 创建时使用 bulk create 加 `ignore_conflicts` 或捕获 IntegrityError 后重算结果。
4. 返回分发前后统计，例如 created、skipped、conflicted。

### 问题 6：我的任务接口最多返回 100 条，前端分页显示不完整

严重级别：中

相关代码：

- `label_studio/projects/workflow_api.py:133`，`TaskSerializer(qs[:100], many=True, ...)`
- `label_studio/projects/workflow_api.py:134`，返回 `count = qs.count()`
- `web/apps/labelstudio/src/pages/MyTasks/MyTasksPage.jsx:16`，前端 page size 包含 200
- `web/apps/labelstudio/src/pages/MyTasks/MyTasksPage.jsx:120`，前端只请求一次接口并本地分页

现象：

后端接口固定只序列化前 100 条任务，但返回总数是完整 `qs.count()`。前端拿到 `results` 后在本地分页，并提供 10、20、50、100、200 的 page size 选项。

风险：

1. 用户实际有超过 100 条待办时，第 101 条之后不会展示。
2. count 和列表长度不一致，分页体验会误导用户。
3. 设置每页 200 时，最多仍只有 100 条。

建议修复：

1. 后端接入 DRF pagination，支持 `page` 和 `page_size`。
2. 前端分页改为服务端分页，每次切页重新请求。
3. 如果短期不做服务端分页，至少把前端 page size 限制到 100，并明确 count 使用当前 results 长度。

### 问题 7：允许配置跨组织人员，但访问链路仍按 active organization 限制

严重级别：中

相关代码：

- `label_studio/projects/workflow_api.py:84`，人员配置时不限制项目 organization 成员
- `label_studio/projects/workflow_api.py:22`，`_visible_org_project()` 按 `request.user.active_organization` 过滤项目
- `label_studio/projects/access.py:10`，`apply_project_team_visibility()` 在已 org scoped 的 queryset 上做团队可见性
- `label_studio/projects/models.py:112`，`Project.objects.for_user()` 先过滤 active organization

现象：

人员配置接口允许把任意用户加入项目团队，注释写明“不再限制须为本项目 organization 成员”。但项目列表、我的任务、workflow API 都先根据用户当前 active organization 筛选项目。如果被配置用户不属于项目 organization，或者 active organization 不匹配，则可能看不到项目，也无法处理任务。

风险：

1. 页面显示“添加人员成功”，但被添加人员无法看到我的任务。
2. 分发到跨组织标注员后，任务会卡在该用户名下。
3. 管理员难以定位任务为什么无人处理。

建议修复：

1. 明确产品规则：是否允许跨组织协作。
2. 如果不允许，则后端配置接口必须校验 user 属于项目 organization。
3. 如果允许，则项目可见性和 `for_user()` 不能只依赖 active organization，需要把显式团队分配作为可见入口。
4. 分发前校验所有待分配用户都能访问项目。

### 问题 8：分配比例校验不足，API 可写入负数或超过 100 的权重

严重级别：中

相关代码：

- `label_studio/projects/workflow_api.py:55`，`TeamAllocationWriteSerializer`
- `label_studio/projects/workflow_services.py:65`，只校验 `sum(weights) > 0`

现象：

`allocation_percent` 字段只定义 Decimal 精度，没有设置 min/max。后端分发只校验总和大于 0，没有要求每个人在 0 到 100 之间，也没有要求总和等于 100。

风险：

1. API 可以写入负数比例。
2. API 可以写入超过 100 的比例。
3. UI 表达的是“百分比分配”，后端实际按权重归一化，语义不一致。
4. 负权重可能导致 largest remainder 算法产生异常或不可预期分配。

建议修复：

1. serializer 增加 `MinValueValidator(0)` 和 `MaxValueValidator(100)`。
2. 对 `label` 角色要求所有比例总和等于 100，允许小数误差范围，例如 0.01。
3. 对非 `label` 角色强制 `allocation_percent = 0`。
4. 后端分发前再次校验，避免绕过前端。

### 问题 9：审核和验收复用同一套编辑器 Accept/Reject 语义，审计与权限语义不清

严重级别：中

相关代码：

- `web/libs/datamanager/src/sdk/lsf-sdk.js:791`，`maybeAdvanceTaskWorkflowAfterReviewDecision()`
- `web/libs/datamanager/src/sdk/lsf-sdk.js:872`，`onAcceptAnnotation()`
- `web/libs/datamanager/src/sdk/lsf-sdk.js:897`，`onRejectAnnotation()`
- `web/libs/editor/src/stores/AppStore.js:718`，`acceptAnnotation()`
- `web/libs/editor/src/stores/AppStore.js:742`，`rejectAnnotation()`

现象：

前端审核和验收都复用 Label Studio 的 `acceptAnnotation`、`rejectAnnotation` 事件。SDK 会先查询当前 workflow stage，如果 stage 是 `review`，调用审核接口；如果 stage 是 `accept`，调用验收接口。

风险：

1. 编辑器层没有真正区分审核模式和验收模式。
2. 按钮文案和底层事件语义可能不一致。
3. 审核/验收是否允许修改 annotation 内容没有明确角色边界。
4. 后续如果增加审核记录、验收记录、意见强制填写，当前复用方式会变得脆弱。

建议修复：

1. 明确 editor mode：`annotate`、`review`、`accept`。
2. 审核和验收使用不同事件或至少传递明确 action type。
3. 后端持久化操作类型、处理人、意见、处理时间。
4. 前端根据 workflow stage 显示不同按钮文案和交互约束。

### 问题 10：缺少 workflow 专项自动化测试

严重级别：中

现象：

仓库中未看到覆盖 `ProjectTeamAllocation`、`TaskWorkflow`、`workflow_services.py` 的专项测试。已有 FSM 测试主要覆盖原有任务、标注、项目状态，不覆盖本次二开的人员分配、审核、验收流程。

风险：

1. 分发、驳回、验收、权限等关键链路缺少回归保护。
2. 当前问题修复后容易再次回归。
3. 前后端双推进、分页截断、跨组织分配等问题难以通过人工完整覆盖。

建议补充测试：

1. 分发比例：多个标注员、不同权重、任务数不能整除时的分配结果。
2. 分发并发：重复分发不抛异常、不重复创建 workflow。
3. 标注后推进：有审核池、无审核池、有验收池、无验收池的分支。
4. 审核驳回：退回原标注员，并要求返工后才能再次推进。
5. 验收驳回：退回原标注员，并保持统计一致。
6. 非当前处理人不能审核、验收、修改 annotation。
7. 我的任务分页超过 100 条时能完整翻页。
8. 跨组织人员配置策略符合产品规则。

## 4. 建议优先级

| 优先级 | 问题 | 原因 |
| --- | --- | --- |
| P0 | annotation 原生接口权限过宽 | 涉及数据越权和绕过工作流 |
| P0 | 驳回后旧 annotation 可再次推进 | 影响审核/验收质量闭环 |
| P1 | `is_labeled` 与 workflow stage 不一致 | 影响列表、统计、队列判断 |
| P1 | 双推进非幂等 | 影响 API 一致性和问题排查 |
| P1 | 我的任务最多 100 条 | 直接影响待办列表完整性 |
| P2 | 分发并发问题 | 管理端偶发异常和部分成功 |
| P2 | 跨组织配置与可见性冲突 | 配置成功但用户不可处理 |
| P2 | 比例校验不足 | 数据质量和分发语义不清 |
| P2 | 审核/验收复用语义不清 | 后续扩展和审计困难 |

## 5. 推荐修复路线

### 第一阶段：先堵权限和闭环漏洞

1. 收紧 `AnnotationAPI` 的 queryset 和对象权限。
2. workflow 项目中，annotation 创建、更新、删除都必须校验当前 stage 和 current assignee。
3. 引入 workflow history 或至少记录当前提交版本，驳回后要求新版本或更新时间晚于驳回时间。
4. 审核/验收决策持久化处理记录，包含处理人、时间、通过或驳回、意见。

### 第二阶段：统一状态和接口行为

1. 明确 workflow 项目的完成态只看 `TaskWorkflow.stage == done`。
2. 修复 `is_labeled` 与 workflow stage 不一致问题。
3. 让 `submit_annotation_after_labeling()` 幂等，或者移除前端显式 submit workflow 调用。
4. 修复我的任务服务端分页。

### 第三阶段：增强配置和分发可靠性

1. 分发逻辑加事务和并发保护。
2. 比例配置增加后端校验。
3. 明确跨组织人员策略，并修正配置校验或可见性。
4. 前端增加配置前校验和分发前风险提示。

### 第四阶段：补测试和审计

1. 增加 workflow service 单元测试。
2. 增加 API 权限测试。
3. 增加驳回返工、验收通过、分页等集成测试。
4. 增加历史数据一致性检查脚本。

## 6. 数据一致性检查建议

可以后续增加管理命令或脚本检查以下异常数据：

1. `TaskWorkflow.stage != 'done'` 但 `Task.is_labeled = True`。
2. `TaskWorkflow.current_assignee_id` 不在对应项目团队角色中。
3. `TaskWorkflow.stage = 'review'` 但项目没有任何 review 角色。
4. `TaskWorkflow.stage = 'accept'` 但项目没有任何 accept 角色。
5. `ProjectTeamAllocation.role = 'label'` 但 `allocation_percent <= 0`。
6. 同一项目 label 角色比例总和不等于 100。
7. 分配给跨组织用户且该用户无法访问项目。
8. 有 workflow 记录但 project.task_workflow_enabled = False。

## 7. 总结

当前二开 workflow 的主干流程已经具备：按比例分发、标注后进入审核、审核后进入验收、驳回退回标注员、完成后置空处理人。但它目前仍是叠加在 Label Studio 原生 annotation/task 机制之上的一层状态表，关键接口、权限、统计和前端交互没有完全统一。

最需要优先处理的是两类问题：

1. 权限绕过：workflow 决策接口严格，但 annotation 原生接口仍可能直接改数据。
2. 返工闭环：驳回后没有绑定新版本，旧 annotation 可以再次满足提交条件。

这两类问题会直接影响标注、审核、验收流程的可信度，应优先修复并补自动化测试。
