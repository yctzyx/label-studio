## 1. 背景与目标

### 1.1 背景

当前平台已具备 `label-studio-ml-backend` 中的 `llm_interactive` 示例能力，支持 Prompt 驱动的文本/图像预标注与交互式标注。但配置方式偏运维导向（环境变量、每项目手动填写 Backend URL），难以支撑多项目、多厂商、多模态的统一管理。

### 1.2 目标


| 目标                | 说明                                                           |
| ----------------- | ------------------------------------------------------------ |
| **界面化模型配置**       | 管理员可在 UI 配置多模态模型、大语言模型及多家厂商（千问、DeepSeek 等）                   |
| **常驻 ML Backend** | 大模型后端作为平台级常驻服务部署，所有项目共用，无需每项目独立起容器                           |
| **项目级 Prompt**    | 每个项目可自定义提示词模板，支持版本管理与预览                                      |
| **原生预标链路**        | 完全复用 Label Studio 的 `Prediction`、Data Manager 批量预测、标注页预标展示机制 |


---

## 2. 现状与问题

### 2.1 当前能力


| 层级                  | 现状                                                                                           |
| ------------------- | -------------------------------------------------------------------------------------------- |
| **ML Backend**      | `llm_interactive` 支持文本/图像/多段落输入；OpenAI / Azure / Ollama；Prompt 模板、交互式标注、批量预标                 |
| **平台连接方式**          | 每个项目单独填写 Backend URL + `extra_params` JSON，偏运维配置                                             |
| **提示词**             | 主要靠环境变量（`DEFAULT_PROMPT`、`PROMPT_TEMPLATE`）或 Label Config 中的 `<TextArea name="prompt">`      |
| **数据模型（已有但未打通 UI）** | `ModelProviderConnection`（组织级 API Key）、`ThirdPartyModelVersion`（含 prompt）、`ModelRun`（批量推理任务） |


### 2.2 核心痛点

1. **配置门槛高**：修改模型需改动 docker-compose / `.env`，非技术人员无法操作
2. **无法统一管理厂商**：千问、DeepSeek 等国内模型没有预设，每个项目重复配置 URL / Key
3. **提示词与项目脱节**：Prompt 散落在环境变量中，无法按项目、按任务类型版本化管理
4. **一项目一 Backend 心智负担重**：期望「一个常驻 LLM 服务、所有项目共用」，而非每个项目独立部署

## 3. 业界参照


| 产品                                   | 可借鉴点                                                                 |
| ------------------------------------ | -------------------------------------------------------------------- |
| **Label Studio Enterprise（Prompts）** | 组织级 Model Provider → Prompt 模板 → Model Version → 批量 Model Run → 预测落库 |
| **Scale / Snorkel**                  | 模型连接与标注任务解耦；Prompt 可版本化、可 A/B 对比                                     |
| **SuperAnnotate**                    | 预标注一键批量；模型健康状态可视化                                                    |
| **Argilla / Dify**                   | 多厂商 OpenAI 兼容网关；UI 选模型而非填 URL                                        |


### 设计原则

保留 Label Studio 原生 `Prediction` + Data Manager「批量获取预测」流程，在其上增加「模型与 Prompt 的可视化配置层」，不另起一套标注体系。

---

## 4. 产品定位

**定位**：组织内统一的「大模型预标注中台」—— 一次部署、多项目复用；管理员配置模型，项目经理配置 Prompt，标注员开箱即用。


| 角色        | 核心诉求                                     |
| --------- | ---------------------------------------- |
| **组织管理员** | 配置千问/DeepSeek/OpenAI 等厂商连接、API Key、预算与权限 |
| **项目经理**  | 为项目选择模型、编写/选择 Prompt 模板、触发批量预标、查看成功率     |
| **标注员**   | 打开任务即可看到预标结果；可选交互式「改 Prompt → 重新生成」      |
| **运维**    | 一个常驻 ML Backend 服务，健康检查、日志、限流            |

## 5. 整体架构

```
┌─────────────────────────────────────────────────────────────────┐
│                     标注平台（Label Studio 二开）                  │
├─────────────────────────────────────────────────────────────────┤
│  【组织设置】模型提供商                                            │
│    通义千问 │ DeepSeek │ OpenAI │ 自定义 OpenAI-Compatible        │
│    API Key / Base URL / 默认模型列表 / 连通性测试                  │
├─────────────────────────────────────────────────────────────────┤
│  【项目设置】大模型预标注                                           │
│    选择提供商 + 模型 │ Prompt 模板 │ 输出映射 │ 预标策略              │
├─────────────────────────────────────────────────────────────────┤
│  【数据管理】批量预标 / 【标注页】交互式 LLM                          │
└──────────────────────────┬──────────────────────────────────────┘
                           │ HTTP（固定内网地址，如 http://llm-ml:9090）
                           ▼
┌─────────────────────────────────────────────────────────────────┐
│              常驻 LLM ML Backend（llm_interactive 增强版）          │
│  - 接收 project_id + prompt_config + provider_config              │
│  - 按 Label Config 解析输出 → Prediction JSON                      │
│  - 支持文本 LLM + 多模态（图像 URL/Base64 → 视觉模型）              │
└─────────────────────────────────────────────────────────────────┘
```

### 关键架构决策


| 决策                    | 说明                                                                                              |
| --------------------- | ----------------------------------------------------------------------------------------------- |
| **常驻服务**              | 平台部署时固定一个 Backend URL（如 `LLM_ML_BACKEND_URL`），所有项目共用；项目差异通过请求上下文（`extra_params` / `setup` 下发）传递 |
| **配置存平台、执行在 Backend** | API Key 存平台数据库（加密），调用时按 `project_id` 注入，避免 Key 写入环境变量                                           |
| **兼容原生机制**            | 项目仍有一个（自动创建的）`MLBackend` 记录，标注员与 Data Manager 无感知                                               |

## 6. 功能模块设计

### 6.1 组织级 — 模型提供商管理

**入口**：组织设置 → **模型提供商**（复用现有 `ModelProviderConnection`，扩展厂商枚举）

#### 预设厂商卡片


| 厂商              | 类型                | 默认 Base URL                                         | 典型模型                               |
| --------------- | ----------------- | --------------------------------------------------- | ---------------------------------- |
| 通义千问（DashScope） | LLM + 多模态         | `https://dashscope.aliyuncs.com/compatible-mode/v1` | qwen-turbo, qwen-plus, qwen-vl-max |
| DeepSeek        | LLM               | `https://api.deepseek.com/v1`                       | deepseek-chat, deepseek-reasoner   |
| 智谱 GLM          | LLM + 多模态         | 官方兼容地址                                              | glm-4, glm-4v                      |
| MiniMax         | LLM + 多模态         | `https://api.minimaxi.com/v1`                         | MiniMax-M3, MiniMax-M2.5, M2-her  |
| OpenAI          | LLM + 多模态         | 官方 API                                              | gpt-4o, gpt-4o-mini                |
| Azure OpenAI    | LLM               | 部署 Endpoint                                         | 按部署名                               |
| Ollama / 本地     | LLM               | 内网地址                                                | 自定义                                |
| **自定义**         | OpenAI Compatible | 用户填写                                                | 用户填写                               |


#### 每条连接配置项

- 显示名称、厂商类型
- API Key（掩码展示，支持轮换）
- Base URL（预设可改，适配私有网关）
- 可选：默认模型列表（支持「拉取模型列表」或手动维护）
- **连通性测试**（发送 hello 请求验证）
- 可选：月度预算上限、告警阈值（复用现有 `budget_`* 字段）

#### 权限

仅组织 Owner / Admin 可增删改；项目经理只能「选用」，不能查看 Key 明文。

---

### 6.2 项目级 — 大模型预标注配置

**入口**：项目设置 → 新增 Tab **「大模型预标注」**（与现有「模型 / Machine Learning」并列或合并）

拆分为 **4 个子区块**：

#### （1）模型选择

- **提供商**：下拉选择组织已配置的连接
- **模型**：下拉（来自 `cached_available_models` 或厂商预设列表）
- **模型类型**（自动推断或手选）：`text` | `vision` | `multimodal`
  - 文本项目默认 text；Label Config 含 `<Image>` 且为图像理解任务时提示选择 vision 模型

#### （2）Prompt 模板

项目经理的核心工作区。

**模板结构**：

```
[System 指令]（可选）
[User 模板正文，支持变量占位符]
```

**内置变量**（与 `llm_interactive` 对齐并扩展）：


| 变量               | 含义                  |
| ---------------- | ------------------- |
| `{text}`         | 主文本对象字段             |
| `{image_url}`    | 图像 URL（多模态）         |
| `{labels}`       | Label Config 中的标签列表 |
| `{task_data.*}`  | 任务 data 任意字段        |
| `{label_config}` | 当前项目标注配置摘要（高级）      |


**Prompt 示例 — 文本分类**：

```
请根据以下文本判断情感倾向，只能从以下标签中选择一个：{labels}

文本：
{text}

只输出标签名称，不要解释。
```

**Prompt 示例 — NER**（需约定 JSON 输出，Backend 解析为 `<Labels>`）：

```
从下列文本中抽取实体，类型为：{labels}
以 JSON 数组输出：[{"start":0,"end":5,"label":"PER"}]

文本：{text}
```

**Prompt 能力**：

- 保存为项目默认 Prompt
- **Prompt 版本**：修改后生成新版本号，预标记录 `model_version` 便于追溯
- **从模板库创建**：平台预置「文本分类 / 实体抽取 / 摘要生成 / 图像描述 / 对话质检」等 starter
- **预览**：选一条样本任务，侧边栏实时查看模型输出（不写入 Prediction）

#### （3）输出映射（Label Config 适配）

自动解析项目 Label Config，让用户确认「模型输出 → 标注控件」映射：


| 标注类型                  | 映射方式                          |
| --------------------- | ----------------------------- |
| `<Choices>`           | 模型输出匹配最近标签（fuzzy match）       |
| `<TextArea>`          | 原文填入                          |
| `<Labels>`（NER）       | Backend 解析 JSON / 结构化输出为 span |
| `<RectangleLabels>` 等 | 二期：视觉模型 + 坐标解析                |


**不兼容时**：配置页显示告警——「当前 Label Config 需包含 Choices 或 TextArea，或联系管理员开启 NER 解析」。

#### （4）预标策略


| 选项        | 说明                                                   |
| --------- | ---------------------------------------------------- |
| 自动预标新导入任务 | 任务入库后异步生成 Prediction                                 |
| 预标范围      | 全部 / 未标注 / 选中子集（与 Data Manager 一致）                   |
| 交互式预标     | 开关：标注页改 Prompt 后 Shift+Enter 触发（对应 `is_interactive`） |
| 置信度阈值     | 低于阈值不展示预标（可选，二期）                                     |
| 并发与限流     | 每项目最大 QPS、批量大小                                       |


**与标注设置联动**：开启后自动设置 `show_collab_predictions` / 预测源为当前 LLM 配置。

---

### 6.3 数据管理 — 批量预标

保持 Label Studio 习惯路径：

**路径**：数据管理 → 勾选任务 → **获取预测** → 选择「大模型预标注（项目配置的名称）」

**增强能力**：

- 弹窗可 **临时覆盖 Prompt**（仅本次批量，不落库）
- 展示进度：总数 / 成功 / 失败 / 预估费用
- 失败任务可导出原因（超时、格式解析失败、API 限流）
- 完成后支持「删除本次 Model Run 产生的预测」（复用 `ModelRun.delete_predictions`）

---

### 6.4 标注页 — 交互式体验

沿用 `llm_interactive` 交互模式：

1. Label Config 保留 `<TextArea name="prompt">`（或由平台注入只读默认 Prompt + 「编辑」按钮）
2. 标注员修改 Prompt → Shift+Enter → Backend 返回新结果
3. 加载态、错误 Toast（Key 失效、模型不存在、内容审核拦截）
4. **多模态**：图像任务在 Prompt 区提示「当前使用视觉模型，图像已自动附带」

---

### 6.5 常驻 Backend 服务设计

在 `llm_interactive` 上增强，而非重写。

**启动**：单实例 Docker / K8s Deployment，平台通过环境变量注入 `LABEL_STUDIO_URL` + 内部 Token。

**请求上下文**（由平台 `setup` / `predict` 传入 `extra_params`）：

```json
{
  "provider": "dashscope",
  "model": "qwen-plus",
  "api_key_ref": "connection:42",
  "prompt_template": "...",
  "system_prompt": "...",
  "temperature": 0.2,
  "output_mode": "choices|textarea|ner_json",
  "use_internal_prompt_template": true
}
```

**厂商适配策略**：统一走 **OpenAI Compatible Client**（千问、DeepSeek、智谱均兼容），减少分支代码。

**多模态处理**：

- 文本模型：`messages[].content = text`
- 视觉模型：`content` 为 `[{type: text}, {type: image_url}]`
- 图像 OCR 兜底：保留现有 Tesseract 路径，作为 vision 模型不可用时的 fallback

**健康检查**：`GET /health` 返回版本、支持的 provider 列表、队列深度。

## 7. 数据模型设计

复用现有表结构，少量扩展，避免两套体系并行。

```
Organization
  └── ModelProviderConnection（扩展 provider 枚举：Qwen, DeepSeek, Zhipu...）
        └── api_key, endpoint, cached_available_models

Project
  └── LLMPreannotationConfig（新建，或扩展 MLBackend.extra_params 为结构化字段）
        ├── model_provider_connection_id
        ├── provider_model_id
        ├── prompt_template / system_prompt
        ├── prompt_version
        ├── output_mode
        ├── is_interactive
        ├── auto_predict_on_import
        └── temperature, max_tokens...

  └── MLBackend（自动创建，url = 全局常驻地址，title = "LLM Preannotation"）
        └── extra_params = 上述配置的快照（供 Backend 读取）

  └── ModelRun（批量预标任务，已有）
        └── 关联 ThirdPartyModelVersion 或新建轻量 LLMModelVersion

Prediction
  └── model_version = "{provider}/{model}/prompt-v3"
  └── model_run_id（批量任务追溯）
```

### API Key 安全

- 平台侧加密存储（`ModelProviderConnection.api_key`）
- Backend 通过短期内部 Token 向平台 API 换取 Key，或平台在转发 predict 时代为调用（视安全边界选择）
- **禁止**在 `extra_params` 中明文传递 Key

## 8. 核心用户流程

### 流程 A：管理员首次开通

1. 部署常驻 `llm-ml-backend` 服务
2. 平台环境变量配置 `LLM_ML_BACKEND_URL`
3. 组织设置 → 添加「通义千问」连接 → 填写 Key → 测试通过
4. 同上添加 DeepSeek（可选）

### 流程 B：项目经理配置项目

1. 创建项目，选择标注模板（如文本分类）
2. 项目设置 → 大模型预标注 → 选择「通义千问 / qwen-plus」
3. 从模板库选择「文本分类」Prompt，填入 `{labels}` `{text}`
4. 点击「预览」，用一条样本验证
5. 保存 → 系统自动注册 / 更新 MLBackend 连接

### 流程 C：批量预标

1. 导入 1000 条任务
2. 数据管理 → 全选 → 获取预测 → 确认
3. 后台 ModelRun 异步执行，进度可见
4. 标注员进入队列，看到预填的 Choices / TextArea

### 流程 D：标注员交互微调

1. 打开任务，默认 Prompt 已填充
2. 修改 Prompt「请更严格判断讽刺」→ Shift+Enter
3. 新预测覆盖展示，满意后提交标注

## 9. 与现有模型设置的关系


| 方案                | 说明                                                         |
| ----------------- | ---------------------------------------------------------- |
| **推荐：分层展示**       | 普通用户只见「大模型预标注」向导式配置；高级用户可展开「ML Backend 详情」查看 URL / 原始 JSON |
| **自动绑定**          | 配置保存时 upsert 一条 `MLBackend`，`url` 固定为全局服务，用户无需手填           |
| **保留自定义 Backend** | 仍允许手动添加 YOLO、NER 等传统 Backend，与 LLM 预标并存                    |

## 10. 非功能需求


| 维度      | 要求                                           |
| ------- | -------------------------------------------- |
| **可用性** | 提供商测试失败时，项目配置页明确报错，不静默失败                     |
| **性能**  | 批量预标走队列（Celery / RQ），支持断点续跑                  |
| **成本**  | 记录 token 用量到 `PredictionMeta`（已有），提供项目级用量报表  |
| **审计**  | Prompt 变更日志：操作人、时间、变更内容                      |
| **合规**  | 数据不出境选项：仅允许选择「本地 Ollama」连接                   |
| **扩展**  | 新厂商 = 注册表加一项 + OpenAI Compatible，无需改动 UI 主流程 |

## 12. 标注类型支持范围

结合 [backend示例与标注类型梳理.md](./backend示例与标注类型梳理.md)：


| 目标场景              | Phase 1      | Phase 2+                |
| ----------------- | ------------ | ----------------------- |
| 文本分类 `<Choices>`  | ✅ 主推         |                         |
| 文本生成 `<TextArea>` | ✅            |                         |
| 对话 / RLHF 类       | ✅ Prompt 定制  |                         |
| NER `<Labels>`    | ⚠️ 需 JSON 协议 | Phase 3                 |
| 图像 OCR / 描述       |              | Phase 2 多模态             |
| 检测框 / 分割          |              | 建议仍用 YOLO / SAM，LLM 作辅助 |


**建议**：MVP 明确主打「文本分类 + 文本生成 + 对话质检」；NER 和视觉框标注在文档中标注为「需 Prompt 协议 + 解析器」，与专用 NER Backend 分工清晰。

> 若目标是「实体抽取 + 直接落 `<Labels toName="text">`」，优先使用 NER 专用 Backend（`huggingface_ner` / `spacy` / `flair`）；`llm_interactive` 需二次开发输出格式后方可用于该场景。

## 13. 总结

本方案的核心设计要点：

1. **一个常驻 LLM Backend**，平台统一地址，项目通过配置区分行为
2. **组织管 Key、项目管 Prompt**，职责清晰，符合 Enterprise 类产品惯例
3. **完全走 Label Studio 原生 Prediction 链路**，不破坏现有 Data Manager、标注页、预标展示逻辑
4. **最大化复用**仓库中已有的 `ModelProviderConnection`、`ModelRun`、`llm_interactive`

### 后续可细化方向

- 页面线框（组织设置 / 项目设置 / 批量预标弹窗）
- API 接口清单
- Phase 1 数据库迁移与 Backend 改造清单
